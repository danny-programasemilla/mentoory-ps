## 1. Executive Summary

Mentoory is a multi-tenant SaaS platform for business incubators, built as a **modular monolith** on ASP.NET Core 10 MVC with SQL Server, designed for eventual microservice extraction. The platform manages incubators, entrepreneurial projects, diagnostic assessments, personalized mentoring plans, learning structures, and mentoring execution.

**Target architecture**: Clean Architecture with DDD, 8 bounded contexts, CQRS via MediatR, server-side rendered UI with Phoenix Admin Template (Bootstrap 5), asynchronous DataTables for listing pages, and in-house authentication with enterprise-grade security. Each bounded context owns its SQL schema, uses its own EF Core DbContext, and communicates cross-domain exclusively through integration events.

**Key architectural decisions**:
- In-house Identity domain replacing ASP.NET Core Identity (per user requirement)
- Cookie-based authentication with server-side session tracking
- PBKDF2-SHA512 password hashing with 600,000 iterations
- EF Core global query filters for multi-tenant data isolation
- Code-defined navigation menus filtered by active role at render time
- MVC Areas organized by user role/perspective, backend organized by bounded context
- SSDT/DACPAC for all database schema management (no EF migrations)
- .NET Aspire for orchestration, health checks, and observability

## Technical Context

**Language/Version**: C# / .NET 10.0 (SDK 10.0.0 with pre-release)
**Primary Dependencies**: ASP.NET Core MVC, MediatR 14.1, FluentValidation 12.1, Mapperly 4.x, EF Core 10.x, MailKit/MimeKit
**Storage**: SQL Server with SSDT/DACPAC schema management, EF Core 10.x ORM
**Testing**: xUnit, Moq, FluentAssertions 8.6, Respawn, Testcontainers, Playwright
**Target Platform**: Linux/Windows server (Azure-ready via Aspire 13.2.0)
**Project Type**: Web application (MVC) — multi-tenant SaaS
**Performance Goals**: 50 concurrent incubators × 100 active projects, sub-200ms p95 for page loads
**Constraints**: Zero-warnings build, Spanish UI, vendor-neutral auth, no EF migrations, no AutoMapper
**Scale/Scope**: ~60 screens, 8 user stories, 8 bounded contexts, 6 user roles

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| # | Principle | Status | Notes |
|---|-----------|--------|-------|
| I | Clean Architecture Layer Boundaries | PASS | 8 bounded contexts, each with Domain/Application/Infrastructure. Web layer uses MediatR only. |
| II | CQRS Pattern Requirements | PASS | All operations via `IBaseRequest`/`BaseCommandHandler`. FluentValidation on all commands. |
| III | DDD Constraints | PASS | Aggregate roots with private setters, `ExternalId` on all external entities, ID-only cross-aggregate refs. |
| IV | Integration Events (ADR-001) | PASS | Cross-domain communication via `INotificationHandler<T>`. Events in originating domain's Application layer. |
| V | Zero-Warnings Policy | PASS | `TreatWarningsAsErrors` enforced. StyleCop configured. |
| VI | DateTime Handling | PASS | `ITimeProvider` in Application; DateTime parameters in Domain. No `DateTime.UtcNow` anywhere. |
| VII | Naming Conventions | PASS | All artifacts follow `{Verb}{Entity}Command`, `{Get|List}{Entity}Query`, etc. |
| VIII | File Organization | PASS | One class per file. JS in `/wwwroot/js/`. SQL in UTF-8. PostDeployment in `/Mentoory.Db.PostDeployment/`. |
| IX | Spanish-First UI | PASS | All user-facing text in Spanish. Code, comments, docs in English. |
| X | SSDT/DACPAC Database Strategy | PASS | Schema in `Mentoory.Db`, seed data via numbered PostDeployment scripts. No EF migrations. |

**Post-Phase 1 Re-check**: All gates remain PASS. The data model, contracts, and project structure align with all 10 constitution principles.

## 3. Domain Decomposition and Bounded Context Definitions

### 3.1 Identity

**Responsibility**: User authentication, credential management, session lifecycle, account status, password policies, email verification, rate limiting, lockout.

**Why separate**: Authentication is a security-critical concern with unique technical requirements (cryptography, token generation, timing-safe comparisons). It changes for security reasons, not business reasons. Extraction-ready as a standalone auth service.

**Aggregates**: User (root), AuthSession (root)
**Owns tables in schema**: `[identity]`
**Key integration events published**: UserRegisteredEvent, UserEmailVerifiedEvent, LoginAttemptEvent, UserLockedOutEvent

### 3.2 Authorization

**Responsibility**: Role assignments, permission checking, active context management, RBAC enforcement.

**Why separate**: Authorization logic (who can do what) is distinct from authentication (who are you). Changes when new roles or permissions are added, independent of auth mechanism. Extraction-ready as a policy service.

**Aggregates**: RoleAssignment (root)
**Owns tables in schema**: `[authorization]`
**Listens to**: UserRegisteredEvent (creates initial role), ParticipantEnrolledEvent (creates project role)

### 3.3 Tenant

**Responsibility**: Incubator management, project management, project lifecycle (stages/transitions), participant enrollment, mentor assignments.

**Why separate**: Core organizational structure of the platform. Incubators and projects are the primary business entities around which all other functionality orbits. Extraction-ready as an organization management service.

**Aggregates**: Incubator (root), Project (root — contains ProjectStage, ProjectParticipant, MentorAssignment as child entities)
**Owns tables in schema**: `[tenant]`
**Key integration events published**: IncubatorCreatedEvent, ProjectCreatedEvent, ProjectStageAdvancedEvent, ParticipantEnrolledEvent

### 3.4 Diagnostic

**Responsibility**: Form templates, project-level form clones, questions, answer options (score/SWOT/ODSR), diagnostic responses, score aggregation, answer corrections.

**Why separate**: Complex domain with its own aggregate hierarchy (templates → clones → questions → options). The scoring logic (aggregation, SWOT/ODSR) is domain-specific. Extraction-ready as an assessment service.

**Aggregates**: FormTemplate (root), ProjectForm (root — contains Question, AnswerOption, FollowUpQuestion), DiagnosticResponse (root — contains QuestionResponse, AnswerCorrection)
**Owns tables in schema**: `[diagnostic]`
**Key integration events published**: DiagnosticCompletedEvent (triggers mentoring plan generation)

### 3.5 Knowledge

**Responsibility**: Knowledge structure templates, project-level clones, hierarchical content (modules → topics → subjects → resources), topic priority configuration.

**Why separate**: The knowledge hierarchy is its own complex aggregate. Topics serve as the bridge entity between diagnostics and mentoring — they define what learning content maps to which assessment questions. Extraction-ready as a content management service.

**Aggregates**: KnowledgeTemplate (root), KnowledgeStructure (root — contains Module, Topic, Subject, Resource)
**Owns tables in schema**: `[knowledge]`

### 3.6 Mentoring

**Responsibility**: Mentoring plan generation and adjustment, session scheduling and logging, assignment creation/submission/review.

**Why separate**: Core value delivery of the platform. Plans, sessions, and assignments share the same lifecycle (plan → execute → review) and the same participants (mentor/entrepreneur). Keeping them together avoids distributed transactions. Extraction-ready as a mentoring service.

**Aggregates**: MentoringPlan (root — contains PlanTopic, PlanApproval), SessionCalendar (root — contains MentoringSession), Assignment (root — contains Submission, ReviewFeedback)
**Owns tables in schema**: `[mentoring]`
**Listens to**: DiagnosticCompletedEvent (auto-generates suggested plan)

### 3.7 Subscription

**Responsibility**: Plan definitions, feature configurations, incubator plan assignments, positive-only overrides, limit enforcement.

**Why separate**: Commercial/licensing concern independent of core business logic. Changes when pricing or feature packaging changes. Extraction-ready as a billing/licensing service.

**Aggregates**: SubscriptionPlan (root — contains PlanFeature, IncubatorOverride)
**Owns tables in schema**: `[subscription]`

### 3.8 Notification

**Responsibility**: Notification composition, delivery tracking, deduplication, scheduling, user preferences, email sending.

**Why separate**: Cross-cutting delivery mechanism that listens to events from all domains. Has its own persistence (delivery logs, preferences) and external integration (SMTP). Extraction-ready as a notification service.

**Aggregates**: Notification (root — contains NotificationRecipient)
**Owns tables in schema**: `[notification]`
**Listens to**: Events from all domains (SessionScheduled, AssignmentCreated, StageAdvanced, etc.)

### 3.9 Shared Kernel

**Not a bounded context** — cross-cutting infrastructure:
- Domain seedwork (Entity, ValueObject, IAggregateRoot, IRepository, IUnitOfWork)
- Application patterns (Result<T>, BaseCommandHandler, IBaseRequest, pipeline behaviors)
- Integration event infrastructure
- Audit logging service
- DataTable request/response patterns
- ITimeProvider, ITenantContext

### Cross-Domain Communication Map

```
Identity ──publishes──→ UserRegisteredEvent ──consumed by──→ Authorization, Notification
Tenant ──publishes──→ ParticipantEnrolledEvent ──consumed by──→ Authorization, Notification
Tenant ──publishes──→ ProjectStageAdvancedEvent ──consumed by──→ Notification
Diagnostic ──publishes──→ DiagnosticCompletedEvent ──consumed by──→ Mentoring
Mentoring ──publishes──→ SessionScheduledEvent ──consumed by──→ Notification
Mentoring ──publishes──→ AssignmentCreatedEvent ──consumed by──→ Notification
```

## 4. Authentication Domain Design

### 4.1 Entities and Value Objects

**User** (Aggregate Root):
- `Id` (long, internal)
- `ExternalId` (Guid, public identifier for routes)
- `Email` (EmailAddress value object — globally unique)
- `NationalIdentity` (value object — Country + NationalId, compound unique per country)
- `FirstName`, `LastName` (string)
- `AccountStatus` (enum: Active, PendingVerification, Locked, Disabled, PasswordResetRequired)
- `LockoutEndUtc` (DateTime? — null when not locked)
- `FailedLoginAttempts` (int)
- `EmailVerifiedAtUtc` (DateTime?)
- `CreatedAtUtc`, `UpdatedAtUtc` (DateTime)
- `_credentials` (private collection of Credential)
- `_emailVerificationTokens` (private collection)
- `_passwordResetTokens` (private collection)

**Credential** (Entity, child of User):
- `Id` (long)
- `HashedPassword` (HashedPassword value object — algorithm, iterations, salt, hash)
- `CreatedAtUtc` (DateTime)
- `IsActive` (bool — only one active credential per user; old ones retained for password history)

**AuthSession** (Aggregate Root):
- `Id` (long, internal)
- `SessionToken` (string — 256-bit cryptographically random, URL-safe Base64)
- `UserId` (long — reference by ID, not navigation)
- `IpAddress`, `UserAgent` (string)
- `CreatedAtUtc`, `LastActivityUtc` (DateTime)
- `ExpiresAtUtc` (DateTime — absolute session lifetime)
- `IsActive` (bool)
- `ActiveIncubatorId`, `ActiveProjectId`, `ActiveRole` (nullable — set after context selection)

### 4.2 Security Controls

**Password Policy** (configurable via appsettings):
- Minimum 12 characters
- Must contain: uppercase, lowercase, digit, special character
- Cannot reuse last 5 passwords (credential history check)
- Maximum age: 90 days (sets AccountStatus = PasswordResetRequired)

**Password Hashing**:
- Algorithm: PBKDF2-HMAC-SHA512
- Iterations: 600,000
- Salt: 128-bit, `RandomNumberGenerator.GetBytes(16)`
- Hash: 256-bit output
- Storage format: `pbkdf2-sha512$600000${base64-salt}${base64-hash}`
- Verification uses timing-safe comparison (`CryptographicOperations.FixedTimeEquals`)

**Account Lockout**:
- Threshold: 5 consecutive failures (configurable)
- Duration: Progressive — 15 min, 30 min, 1 hour (configurable)
- Reset: Counter resets on successful login
- Admin override: Manual unlock via DeactivateAccountLockout command

**Rate Limiting** (ASP.NET Core middleware):
- Login: 5 requests / 15 min / IP
- Registration: 3 requests / 15 min / IP
- Password reset: 3 requests / 60 min / email+IP

**Email Verification**:
- Token: 256-bit cryptographically random, URL-safe Base64
- Storage: Hash of token stored (never plaintext)
- Expiry: 24 hours
- One active token per user (new request invalidates old)

**Password Reset**:
- Same token generation as email verification
- Expiry: 1 hour
- Generic response on public endpoint (FR-052 — no information disclosure)
- Single use: Token invalidated after successful reset

### 4.3 Session Lifecycle

```
Login Request
  │
  ├─ Validate credentials (timing-safe)
  │   ├─ FAIL: Increment FailedLoginAttempts
  │   │         If threshold reached → Lock account, publish UserLockedOutEvent
  │   │         Return generic "Credenciales inválidas" (FR-052)
  │   └─ SUCCESS: Reset FailedLoginAttempts
  │
  ├─ Check AccountStatus
  │   ├─ PendingVerification → "Verifique su correo electrónico"
  │   ├─ Locked → "Cuenta bloqueada temporalmente"
  │   ├─ Disabled → "Cuenta deshabilitada"
  │   ├─ PasswordResetRequired → Redirect to password change
  │   └─ Active → Continue
  │
  ├─ Invalidate any existing active sessions (FR-007 — single session)
  │
  ├─ Create AuthSession record
  │   ├─ Generate SessionToken (256-bit random)
  │   ├─ Set LastActivityUtc = now
  │   ├─ Set ExpiresAtUtc = now + absolute timeout (e.g., 8 hours)
  │   └─ Publish LoginAttemptEvent (success, for audit)
  │
  ├─ Set authentication cookie
  │   ├─ Value: SessionToken
  │   ├─ HttpOnly: true
  │   ├─ Secure: true
  │   ├─ SameSite: Strict
  │   └─ Path: /
  │
  └─ Redirect to context selection (or auto-select per FR-009)

On Each Request (middleware):
  │
  ├─ Read SessionToken from cookie
  ├─ Load AuthSession from database
  ├─ Validate: IsActive, not expired, LastActivityUtc within inactivity timeout
  │   ├─ INVALID → Clear cookie, redirect to login
  │   └─ VALID → Update LastActivityUtc, set ClaimsPrincipal
  │
  └─ Set ITenantContext from session's ActiveIncubatorId

Logout:
  ├─ Mark AuthSession as inactive
  ├─ Clear authentication cookie
  └─ Redirect to login page
```

### 4.4 Registration Workflows

**Open Registration** (FR-046 through FR-054):
1. User submits: country, national ID, email, password, first name, last name
2. Validate password strength
3. Check NationalIdentity uniqueness (country + national ID)
4. Check Email uniqueness
5. If either fails → return generic error "No fue posible completar el registro" (FR-052)
6. Create User with AccountStatus = PendingVerification
7. Create Credential with hashed password
8. Generate EmailVerificationToken
9. Publish UserRegisteredEvent (triggers verification email)
10. Show "Revise su correo electrónico para verificar su cuenta"

**Administrative Enrollment** (FR-053):
1. Admin submits: country, national ID, email, first name, last name, target incubator, project, role
2. Validate NationalIdentity uniqueness → specific error if conflict
3. Validate Email uniqueness → specific error if conflict
4. Create User with AccountStatus = PasswordResetRequired
5. Generate temporary password or send activation link
6. Publish UserRegisteredEvent + ParticipantEnrolledEvent

## 5. Authorization and Dynamic Menu Strategy

### 5.1 Role-Based Access Control

**Roles** (PlatformRole enum):
- `GlobalAdmin` — Platform-wide administration
- `IncubatorAdmin` — Incubator-level administration
- `ProjectCoordinator` — Project management and coordination
- `Mentor` — Mentoring sessions and plan review
- `Entrepreneur` — Diagnostic completion and learning
- `Sponsor` — Read-only project dashboards

**RoleAssignment** entity binds a user to a specific incubator/project/role combination. One user can have multiple RoleAssignments (FR-002).

**Context Selection** (FR-005 through FR-009):
- After login, query RoleAssignments for the authenticated user
- If exactly one combination → auto-select (FR-009)
- If multiple → show context selection page with cards
- Selected context stored in AuthSession (ActiveIncubatorId, ActiveProjectId, ActiveRole)
- All subsequent authorization checks use the active context

### 5.2 Authorization Enforcement

**Controller level**: `[Authorize(Roles = "GlobalAdmin,IncubatorAdmin")]` on controllers/actions

**Middleware level**: `TenantContextMiddleware` reads the active context from AuthSession and sets `ITenantContext` for EF Core global query filters.

**Application level**: Commands/queries can include context validation via the handler (e.g., verify the user's active project matches the requested resource).

**Defense in depth** (FR-013):
1. Cookie authentication middleware (is the user authenticated?)
2. Role-based authorization attribute (does the user's active role allow this action?)
3. Tenant context filter (is the data scoped to the active incubator?)
4. Application-level validation (does the specific resource belong to the active project?)

## 8. Data Access and SQL Server Persistence Strategy

### 8.1 Schema-Per-Bounded-Context

Each bounded context owns a SQL schema:
- `[identity]` — Users, Credentials, AuthSessions, tokens
- `[authorization]` — RoleAssignments
- `[tenant]` — Incubators, Projects, ProjectStages, Participants, MentorAssignments
- `[diagnostic]` — FormTemplates, ProjectForms, Questions, AnswerOptions, Responses
- `[knowledge]` — KnowledgeStructures, Modules, Topics, Subjects, Resources
- `[mentoring]` — MentoringPlans, PlanTopics, SessionCalendars, Sessions, Assignments
- `[subscription]` — SubscriptionPlans, PlanFeatures, IncubatorOverrides
- `[notification]` — Notifications, Recipients, Preferences
- `[audit]` — AuditLog (cross-cutting)

### 8.2 One DbContext Per Bounded Context

Each bounded context has its own `DbContext` subclass of `SharedAbstractDbContext`. This ensures:
- Schema isolation at the ORM level
- Independent migration/deployment per context
- Clear ownership of tables
- No accidental cross-context joins

The existing `DbContextFactory` pattern maps request namespaces to DbContext types. Extended for all 8 contexts:

### 8.3 Multi-Tenant Query Filters

Tenant-scoped entities implement `ITenantEntity`:

```csharp
public interface ITenantEntity
{
    long IncubatorId { get; }
}
```

Each tenant-scoped DbContext applies global filters:

```csharp
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    foreach (var entityType in modelBuilder.Model.GetEntityTypes())
    {
        if (typeof(ITenantEntity).IsAssignableFrom(entityType.ClrType))
        {
            var parameter = Expression.Parameter(entityType.ClrType, "e");
            var property = Expression.Property(parameter, nameof(ITenantEntity.IncubatorId));
            var tenantId = Expression.Property(Expression.Constant(_tenantContext), nameof(ITenantContext.CurrentIncubatorId));
            var filter = Expression.Lambda(Expression.Equal(property, tenantId), parameter);
            modelBuilder.Entity(entityType.ClrType).HasQueryFilter(filter);
        }
    }
}
```

### 8.4 Database Deployment

- **Schema authoring**: SSDT SQL project (`Mentoory.Db/`)
- **Build**: `dotnet build Mentoory.Db/MentooryDb.sqlproj` → produces DACPAC
- **Deploy**: `SqlPackage /Action:Publish /SourceFile:MentooryDb.dacpac /TargetConnectionString:...`
- **Seed data**: Post-deployment scripts in `Mentoory.Db.PostDeployment/`, numbered sequentially, idempotent (DELETE/INSERT pattern)
- **Indexes**: One DDL file per index in `{schema}/Indexes/` directory

### 8.5 ExternalId Strategy

All entities exposed in URLs use `ExternalId` (Guid), never internal `Id` (long):
- Routes: `/Administration/Projects/{externalId}`
- Repositories: `GetByExternalIdAsync(Guid externalId)`
- Internal IDs used only for foreign keys and internal references

Each bounded context registers its DbContext through Aspire:

```csharp
public static IHostApplicationBuilder AddIdentityInfrastructure(
    this IHostApplicationBuilder builder,
    string connectionName = "DefaultConnection")
{
    var connectionString = builder.Configuration.GetConnectionString(connectionName)
        ?? throw new InvalidOperationException($"Connection string '{connectionName}' not found.");

    builder.Services.AddDbContext<IdentityDbContext>(opts =>
        opts.UseSqlServer(connectionString));

    builder.EnrichSqlServerDbContext<IdentityDbContext>(settings =>
        settings.CommandTimeout = 30);

    builder.Services.AddScoped<IUserRepository, UserRepository>();
    builder.Services.AddScoped<IAuthSessionRepository, AuthSessionRepository>();
    return builder;
}
```

## 13. Risks, Tradeoffs, and Early Validation Decisions

### 13.1 Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| In-house auth has security vulnerabilities | Critical | Follow OWASP guidelines strictly. Security-focused code review. Penetration testing before production. Use well-tested cryptographic primitives (.NET built-in). |
| 8 bounded contexts = many projects | Complexity | Start with Identity + Tenant + Authorization. Add remaining contexts incrementally. The Example project proves the pattern first. |
| Phoenix Admin Template limitations | Medium | Phoenix is mature and extensible. If a specific component is missing, build it with Bootstrap 5 (no external libraries per constitution). |
| Multi-tenant query filter bypass | Critical | Integration tests specifically verify isolation (SC-006). Code review policy: any use of `IgnoreQueryFilters()` requires explicit justification. |
| Session validation on every request hits DB | Performance | Cache active sessions in `IMemoryCache` with 60-second sliding expiration. Invalidation clears cache entry. At scale, replace with Redis via Aspire. |
| DACPAC deployment on large databases | Downtime | For structural changes, test on staging with production-size data. Use `SqlPackage /p:BlockOnPossibleDataLoss=true` to prevent accidental data loss. Schedule maintenance windows for schema changes. |

### 13.2 Tradeoffs

| Decision | Tradeoff | Justification |
|----------|----------|---------------|
| PBKDF2 over Argon2id | Not memory-hard (less resistant to GPU attacks) | Built into .NET, no external dependency for security-critical code. Upgradeable via versioned hash format. |
| Code-defined menus over DB-driven | Less flexible for admin-managed menu changes | Menu changes are infrequent and should go through code review. Avoids CRUD overhead and eliminates a class of security bugs. |
| Single SQL database with schema isolation over separate databases | Less isolation than DB-per-tenant | Simpler operations, single connection string, cross-context reporting possible. Adequate for 50 incubators (SC-009). |
| Areas by role over Areas by bounded context | One area may span multiple bounded contexts | Matches user mental model. Users think "I'm a coordinator" not "I'm in the Diagnostic domain." |
| No distributed cache initially | Session validation hits SQL on cache miss | Simpler infrastructure for initial deployment. Redis can be added via Aspire when load justifies it. |

### 13.3 Validate Early

1. **Authentication flow end-to-end**: Build login → session → context selection as the first deliverable. Validates cookie middleware, session management, and RBAC before anything else.
2. **Multi-tenant isolation**: Create two test incubators, verify complete data isolation before building business features.
3. **DataTable server-side processing**: Build one listing page (e.g., list incubators) to validate the reusable pattern before replicating across all list pages.
4. **DACPAC deployment pipeline**: Test the full DACPAC build → deploy cycle in CI before accumulating many schema changes.
5. **Phoenix sidebar navigation**: Render the dynamic menu with role filtering to validate the UX approach before building all pages.

## 14. Phased Implementation Approach

### Phase 1: Foundation (User Story 1 — P1)

**Goal**: Working multi-tenant platform with authentication, authorization, and basic incubator/project management.

**Deliverables**:
- Solution scaffolding (all projects, references, DI registration)
- Identity domain: Registration, login, logout, session management, email verification, password reset, lockout
- Authorization domain: Role assignments, context selection, RBAC enforcement
- Tenant domain: Incubator CRUD, Project CRUD (basic), participant enrollment
- UI: Phoenix Admin sidebar layout, dynamic menu, login/register pages, incubator list/detail, project list/detail
- Audit: Cross-cutting audit logging
- Database: `[identity]`, `[authorization]`, `[tenant]`, `[audit]` schemas with SSDT
- Testing: Unit tests for Identity + Tenant + Authorization, integration tests for auth flow and multi-tenant isolation
- CI/CD: GitHub Actions CI pipeline (build + test)
- Remove `Mentoory.Example.*` projects after validation

**Validates**: Authentication security, multi-tenant isolation, role-based menus, DataTable pattern, DACPAC pipeline

### Phase 2: Diagnostic Module (User Story 2 — P2)

**Goal**: Complete diagnostic assessment lifecycle from template to response.

**Deliverables**:
- Diagnostic domain: Form templates, cloning, questions, answer options (score/SWOT/ODSR), follow-up questions
- Diagnostic responses: Initial evaluation submission, score aggregation per topic
- Answer correction with audit trail
- Sync modes for cloned forms
- UI: Form template management (Platform area), form cloning/customization (Coordination area), diagnostic form completion (Participant area)
- Testing: Unit tests for scoring logic, integration tests for clone/submit flow

### Phase 3: Knowledge Structure (User Story 3 — P3)

**Goal**: Hierarchical learning content management with template cloning.

**Deliverables**:
- Knowledge domain: Templates, structures, modules, topics, subjects, resources
- Clone/customize pattern (reuse from Diagnostic)
- Topic ↔ diagnostic question linking
- Topic priority score range configuration
- UI: Knowledge structure tree view (jsTree), resource management, template browsing
- Testing: Unit tests for hierarchy operations

### Phase 4: Mentoring Plan + Execution (User Stories 4 & 5 — P4/P5)

**Goal**: Core value delivery — from diagnostic scores to mentoring execution.

**Deliverables**:
- Mentoring domain: Plan generation from diagnostic scores, priority mapping, collaborative adjustment, approval
- Session scheduling engine, session logging, topic tracking
- Assignment creation, submission, review workflow
- Integration: DiagnosticCompletedEvent → auto-generate suggested plan
- UI: Plan review/adjustment page (Mentoring area), session calendar, assignment management
- Testing: Unit tests for plan generation logic, integration tests for full diagnostic→plan flow

### Phase 5: Subscriptions + Lifecycle (User Stories 6 & 7 — P6/P7)

**Goal**: Commercial controls and operational governance.

**Deliverables**:
- Subscription domain: Plan management, feature configuration, overrides, limit enforcement
- Tenant domain extension: Full project lifecycle (7 stages), stage transitions, stage-driven UI
- UI: Subscription management (Platform area), lifecycle stage indicator and transition controls (Coordination area)
- Testing: Unit tests for feature limit enforcement, lifecycle stage transitions

### Phase 6: Notifications + Hardening (User Story 8 — P8)

**Goal**: Production readiness.

**Deliverables**:
- Notification domain: Email composition, delivery tracking, deduplication, scheduling, preferences
- MailKit integration for SMTP delivery
- E2E tests: All 10 critical user journeys with Playwright
- Performance testing: Verify SC-009 (50 incubators × 100 projects)
- Security review: Penetration testing for auth flows
- CI/CD: Staging and production deployment pipelines
- Documentation: API contracts, deployment runbook
